## 0. Terms

- **Text cell**: a cell of a field whose type is RichText (`0`).
- **Type id** of a stored value: an integer-valued number gives that integer (`0`, `0.0`, `6`); a string of ASCII digits with an optional leading `-` gives its integer (`"0"`, `"6"`; older web clients stored strings, `web:src/application/database-yjs/cell.field-type.ts:73-80`). Anything else (absent, `null`, a boolean, `""`, `"abc"`, `1.5`) has no type id.
- **Text-written cell**: a cell whose `field_type` has no type id or has type id `0`, **or** whose legacy `source_field_type` has type id `0` (conformance `env-045` to `env-053`). Only a Text-written cell's `rich_text` can describe its text. Every reader and every guard on both clients MUST use exactly this definition. In particular:
  - it never falls back to the field's current type (the web's `getStoredCellFieldType(cell, fallback)` does, `cell.field-type.ts:27-33`; it stays for decoding `data`, not for this decision);
  - it is the union of the two readings that exist today. Rust reads only `field_type`, and its `get_as::<i64>` reads a string as "no type", so `"6"` counts as Text-written (RT:164-173). The web prefers `source_field_type` (`cell.field-type.ts:27-33`, `cell.parse.ts:59-68`). The union protects every cell either reading protects.
- **Bookkeeping keys**: `field_type`, `source_field_type`, `last_modified`, `created_at`. A write that would change only these keys changes nothing a reader shows (R49).
- **This version**: format version 1, the first versioned release of both clients.
- **Writer version** (`v`): the format version of the client that wrote an envelope.
- **Newer cell**: a Text-written cell whose `rich_text` is in state `newer` (section 3). This version shows it but never changes it.
- **Loss**: a write loses data when, after it, no reader of the writer's version or of any newer version can get formatting it could get before the write. Making formatting stale (section 3) is loss, because staleness is permanent for every version.

## 1. Storage model and frozen invariants

A Text cell is a Yjs map. Its formatting is stored beside its plain text:

| Key | Type | Meaning |
|---|---|---|
| `data` | string | The plain text. Filters, sort, group, search, export, AI indexing, formulas and released clients read only this key (WRT:5-15; RT:1-9). |
| `rich_text` | string (JSON) | The formatting envelope (section 2). It is absent if the cell was never formatted. `""` means the formatting was cleared (RT:135-147). |
| `field_type`, `created_at`, `last_modified` | | Unchanged. |

The following invariants are frozen. No future version may change them, because older clients enforce them and cannot be updated in place.

- **R1.** `data` MUST always be the complete plain text of the cell, as a reader that knows nothing about formatting should see it.
- **R2.** `rich_text`, when it is present and not `""`, MUST be a JSON string whose top-level value is an object with a string member `text`.
- **R3 (staleness).** Every reader of every version MUST ignore an envelope whose `text` is not exactly equal to `data`. A writer that changes `data` without writing new formatting thereby retires the old formatting.
- **R4.** A future representation of formatting that is not a JSON string (for example a nested Y.Map, to merge concurrent edits) MUST use a new cell key, and MUST carry its own copy of the text so that R3 can apply to it. Version 1 never writes, removes or reads such keys. Version 1 also never removes cell keys it does not know: web writes set keys one by one (`web:src/application/database-yjs/dispatch/cell.ts:217-241`), and Rust writes merge keys into the stored map (DER:1583-1589).
  - Such a key MUST be a `Y.Map` or `Y.Array` whose leaves are JSON values. `Y.Text`, `Y.XmlFragment` and other shared types are not allowed until a later version verifies that every version 1 copy path (R47, including Rust `duplicate_row`) copies them.
  - Version 1 copy paths MUST deep-copy every shared Yjs value they meet (R47). Re-inserting the same `Y.Map` instance throws in Yjs (`YMap._integrate` reads a `_prelimContent` that is `null` once integrated) and leaves a partial cell.
- **R5.** A future version that needs older clients to stop editing a cell MUST say so with `min_v` (section 4). It MUST NOT depend on older clients noticing anything else.

## 2. The envelope

### 2.1 Fields

```json
{"v": 1, "text": "Ask @Ada", "delta": [{"insert": "Ask "}, {"insert": "@", "attributes": {"mention": {"type": "person", "person_id": "u1", "person_name": "Ada", "label": "@Ada"}}}]}
```

| Field | Required | Type | Meaning |
|---|---|---|---|
| `v` | written by every versioned writer | integer ≥ 1 | The writer version. It is informational only: readers MUST NOT decide anything from it (R12). A missing `v` reads as 1. |
| `min_v` | no | integer ≥ 1 | The oldest format version that can edit this cell without loss. A missing `min_v` reads as 1. Version 1 never writes it. |
| `text` | yes | string | The `data` this formatting was saved for (R3). |
| `delta` | yes | array | Quill-style list of inserts (section 5). |
| anything else | no | | Reserved. Readers ignore it. Version 1 writers drop it. A future version that needs older writers to keep a top-level field MUST set `min_v` (R5). |

### 2.2 Parsing (normative order)

A reader MUST compute a cell's **state** with exactly these steps, in this order. The order matters: for example, staleness is decided before versions are compared, so a stale newer envelope is editable (conformance `env-019`).

1. **Field types.** If the cell is not Text-written (section 0), the state is `plain` and the formatting is ignored. If the cell is Text-written but the field is not Text, compute the state anyway, because it decides editability. Display the cell as `plain` (conformance `env-033`, `env-034`, `env-046`, `env-050`). This matches today's readers (RT:77-83, 164-173; `web:.../cell.parse.ts:68`) except for the forms section 0 pins down.
2. **Value type.** If `rich_text` is absent, `null`, or `""`, the state is `plain`. If it is present but not a string, the state is `newer` (R6).
3. **JSON.** Parse the **whole** string as a JSON value. If parsing fails because the input is malformed, the state is `invalid`. If parsing instead reaches a resource limit, such as serde_json's nesting limit, the state is `newer` with no readable delta: the reader cannot safely decide validity, staleness, or `min_v` and MUST prevent destructive edits. Readers MUST retain their parser's safety limits. Parsing also fails if any number anywhere in the value is outside the finite double range, or if any string or object key anywhere contains an unpaired UTF-16 surrogate escape. serde_json rejects both when it builds a `serde_json::Value` (it reports "number out of range" and "unexpected end of hex escape"; checked against serde_json 1.0.140, the version in `Cargo.lock`). The web and Dart parsers accept them, so they MUST reject them explicitly (R7). Rust MUST build the `Value` (R8): a derived struct skips the fields it does not name without validating them (conformance `env-042` to `env-044`).
4. **Shape.** If the value is not an object, or `text` is missing or is not a string, the state is `invalid`.
5. **Staleness.** If `text !== data`, the state is `stale` (R3).
6. **Version gate.** Read `min_v` with the rule in 2.3. If the value is not satisfied by this version, the state is `newer`.
7. **Delta structure.** `delta` MUST be an array of objects. Each object needs a string `insert`, and `attributes` that are missing, `null`, or an object (RT:233-242; WRT:172-184). If the state is not yet `newer`, a structural failure makes it `invalid`. If the state is `newer`, a structural failure only means there is no delta to show: show `data` (conformance `env-010`).
8. **Sanitize** the delta (sections 6-9).
9. **Plainness.** If no insert has any attribute left after sanitizing (known or preserved), the state is `plain`. Otherwise it is `rich`. A `newer` envelope stays `newer` even if it formats nothing this version knows (conformance `env-039`).

- **R6.** A `rich_text` that is not a string MUST be treated as `newer`. Version 1 never writes one. Under R4 it can only come from a future representation, so it must not be destroyed.
- **R7.** The web and Dart parsers MUST treat non-finite numbers and lone surrogates (in values and in keys) as a parse failure, as serde_json does. Otherwise the clients would disagree about whether a cell is `invalid`, `rich` or `newer` (conformance `env-018`, `env-035`, `env-042` to `env-044`). On the web, use a `JSON.parse` reviver that checks both its `key` and its `value` arguments; in Dart, a `jsonDecode` reviver that does the same. Results are cached by raw string (WRT:220-247), so the reviver's cost is paid once per value.
- **R8.** If an object has duplicate keys, the last one wins. JSON.parse, Dart's `jsonDecode` and `serde_json::Value` all behave this way (conformance `env-036`, `env-041`). A serde **derived struct** does not: it fails with "duplicate field". So Rust MUST decide the state from one `serde_json::from_str::<Value>` of the whole envelope, and MUST NOT use a derived header struct (such as today's `describes_text`, RT:175-185) for any decision that affects state or editability.

### 2.3 Reading `min_v` and `v`

- **R9.** `null` reads as absent, for both `min_v` and `v`. Dart's `map['min_v']` cannot tell them apart anyway (conformance `env-016`).
- **R10.** `min_v` is satisfied by version N only if it is absent, or if it is a JSON number that is finite, has no fractional part, is ≥ 1, and is ≤ N. Integer-valued numbers count as integers: `1.0` is 1 (conformance `env-007`). Rust MUST use `as_f64()` plus a fraction check, because `as_i64()` returns `None` for `2.0` (checked). Dart MUST NOT call `toInt()` or `truncate()` on doubles that may be out of range; use `value == value.roundToDouble()` instead (conformance `env-017` is `1e300`).
- **R11 (safe default).** Every other `min_v` makes the cell `newer`, and so read-only. This includes strings, booleans, fractions, 0, negative numbers, arrays and objects (conformance `env-011` to `env-015`). A malformed requirement must never lead to an edit that could destroy data.
- **R12.** `v` MUST NOT gate anything. A malformed `v` is ignored (conformance `env-030`). Writers MUST write their own version as an integer.

## 3. States and reader rules

| State | Show | Edit (this version) | Write behavior |
|---|---|---|---|
| `plain` | `data` | yes, rich editor | as today |
| `invalid` | `data` | yes, rich editor, starting from `data` | Like `plain`. Under R2, R7 and R10 no conforming writer can produce it, so it is corruption, and the next write that changes `data` clears it (web deletes the key, `web:.../dispatch/cell.ts:223-231`; Rust writes `""`, RT:139-147). |
| `stale` | `data` | yes, rich editor, starting from `data` | Like `plain` |
| `rich` | sanitized delta | yes | Section 11 |
| `newer` | the sanitized delta if it is structurally valid, else `data`; with a read-only affordance | **no** | A write that would change only bookkeeping keys is a silent no-op; every other write is refused (R49); bulk schema operations skip the cell (R49b) |

- **R13.** Renderers MUST NOT render preserved (unknown) attributes, and MUST NOT pass them to style or URL sinks (section 8).
- **R14.** When a reader shows a `newer` cell, it SHOULD show the known formatting. It MUST show unknown mention types by their `label` (section 9), and MUST mark the cell as read-only. Editing entry points MUST show the update prompt instead of an editor (section 14).

## 4. Version semantics: when to bump `v`, when to set `min_v`

- **R15.** A release that starts writing anything an earlier release does not write MUST raise its `v`. Examples: a new key, a new value domain for a key, or a new mention type.
- **R16.** A writer MUST compute `min_v` from the content it is writing at that moment: the highest "min version" of any feature the content uses (table below). It MUST leave `min_v` out when that is 1. It recomputes `min_v` on every write, so removing the last embed lowers `min_v` again. Version 1 always leaves `min_v` out.
  - The content includes everything the writer writes back, **including preserved content it does not understand**. In particular, a preserved value that breaks an earlier version's section 8 limits requires `min_v` above that version (R28).
  - Each version's feature table MUST be cumulative: it lists every non-additive feature of every version up to its own, including every earlier version's preservation limits. Recomputation is then sound: a stored `min_v` of k ≤ N can only come from features of versions up to k, which version N's table knows.
- **R17.** A feature is **additive**, and needs no `min_v`, only if all three hold:
  1. a version 1 reader that drops nothing but what sections 6-8 drop keeps it intact;
  2. version 1's plain-text rule (section 10) produces the same `data` for it as the new writer does;
  3. text typed or deleted around it by version 1 leaves it meaningful.

  Every other feature MUST set `min_v` to the first version that understands it.

| Future feature | Additive? | Why |
|---|---|---|
| New on/off mark (`superscript: true`) | yes | It is preserved as an unknown attribute (section 8). Typed text inherits it (section 8.4). |
| New valued attribute (`font_size: 14`, `font_family: "Inter"`) | yes, while it meets the section 8 limits | It is preserved. A value that breaks the limits is not additive. |
| New mention type, or new fields on a mention | yes, if every mention carries `label` | Version 1 writes the `label` into `data` (section 10) and keeps the fields (section 9), including `false` values (R29). |
| Quill line attributes on `"\n"` inserts (`{"insert":"\n","attributes":{"list":"bullet"}}`) | **no** | They fail R17.3. Both editors treat a line attribute as an ordinary run attribute: Desktop's Enter slices the attributes of the text before the caret (`dt:lib/plugins/database/widgets/cell/rich_text/rich_text_cell_shortcuts.dart:241-247`), so a new plain `"\n"` moves the bullet to the wrong line; typing at the start of the next line inherits the newline's `_preserved` (`dt:lib/plugins/document/presentation/editor_globals.dart:84-95`) and R33 then merges it into text (`{"insert":"\nx","attributes":{"list":"bullet"}}`). The web's Enter inserts `"\n"` into the current text node (`web:.../rich-text-slate.ts:452-457`) with the same effect. |
| Keys on an insert other than `insert` and `attributes` (for example `{"insert":"x","id":"…"}`) | **no** | Every version 1 writer rebuilds inserts as `{insert, attributes}` (`slateValueToRichText`, `web:.../rich-text-slate.ts:106-137`; Dart `normalizeRichTextCellDelta`, ES:96-128), so the keys are dropped. |
| Embeds (`insert` that is not a string), `retain` or `delete` ops | **no** | Version 1 rejects them as structurally invalid (RT:233-242). |
| A new atom kind that is not a mention (a new placeholder attribute) | **no** | Version 1 treats the placeholder as text, so its plain text would change. Express new atoms as mention types with `label`. |
| A new placeholder character for atoms | **no** | Version 1 only recognizes `$` and `@` (ES:77; `web:.../rich-text-slate.ts:26`). |
| A changed meaning or value type of a registered key (section 6) | **no** | Version 1 sanitizes registered keys by the version 1 rules. |
| A changed plain-text rule for a known mention type | **no** | `data` would differ depending on which client saved last. |
| A top-level envelope field that must survive edits | **no** | Version 1 writers drop unknown top-level fields. |
| Anything that changes how `text` relates to `data` | forbidden | R1 and R3 are frozen. |

Linear `min_v` was chosen over a list of required feature names (for example `"req": ["embeds"]`). Both clients ship in lockstep, so a feature list would add parsing and test surface for no gain. A future version can still add one under a new top-level key and set `min_v` to its own version.

## 5. Delta model

- **R18.** A delta is an array of `{insert: string, attributes?: object|null}`. Version 1 writers MUST write only non-empty string inserts. They MUST omit empty `attributes`, and MUST NOT write attributes whose value is `null` or `false`. Inside the formatting, `null` and `false` mean "absent" for every key, known or unknown, at the top level of `attributes` (RT:244-257; `web:.../rich-text.ts:186-193`). This is frozen: a future attribute cannot give `false` its own meaning. The freeze covers only the top level of `attributes`. Inside a mention object, `false` is a value and is kept (R29).
- **R19.** Line breaks are `"\n"` characters inside inserts. A cell has no blocks (`web:src/components/database/components/cell/text/rich-text/rich-text-slate.ts:9-15`). Attributes on a `"\n"` insert are preserved like any other attributes, but a future writer that gives them line semantics MUST set `min_v` (section 4).
- **R20.** Readers MUST NOT require the inserts to spell `text`. Today's Rust code does not check this (RT:116-120; integration test `rich_text_cell_test.rs:348-367`).
- **R21.** Writers MUST NOT write strings containing lone surrogates, in `data` or anywhere in the envelope: inserts, attribute values at any depth, object keys, mention fields and labels, and `text`. The web MUST replace them with U+FFFD in every string of the labelled delta, and in `data`, before it serializes (`String.prototype.toWellFormed`, or an equivalent walk). `JSON.stringify` writes a lone surrogate as a `\udXXX` escape, which every reader then rejects (R7), so the formatting would be silently lost.

## 6. Attribute registry (known keys)

Every key in this table is sanitized by its rule. A value that breaks the rule is dropped (the key is removed), and the rest of the insert is kept.

| Key | Value | Sanitization | Render sink |
|---|---|---|---|
| `bold`, `italic`, `underline`, `strikethrough`, `code` | `true` | Kept only if exactly `true` (WRT:152-155; ES:195-197) | Element/style mapping (R25) |
| `href` | string | Kept if it is a non-empty string, with no length cap of its own: the delta limit bounds it. This matches the user's uncommitted removal of `MAX_MARK_VALUE_LENGTH` (WRT:157-160) and Desktop's acceptance of hrefs over 32 KB. | MUST go through the platform URL policy: web `openUrl`/`processUrl` (`web:src/utils/url.ts:109-142`); desktop `afLaunchUrlString` / `rich_text_cell_links.dart` |
| `formula` | string | Kept if it is a non-empty string. It is meaningful only on a placeholder. | KaTeX (web) / `Math.tex` (desktop), with no trust or HTML extensions |
| `font_color`, `bg_color` | color string | Kept if it is at most 64 characters and matches the color grammar (R22) | `renderColor` (web), `richTextCellHexColor` (desktop) |
| `af_text_color`, `af_background_color` | color string | Same as above | Theme token lookup |
| `mention` | object | Section 9. A JSON string that decodes to an object is accepted and written back as an object. | Mention renderers |

- **R22 (color grammar).** A color value is one of:
  - hex: `^(#|0x)([0-9A-Fa-f]{6}|[0-9A-Fa-f]{8})$`
  - rgb or rgba: `^rgba?\(\s*\d{1,3}\s*,\s*\d{1,3}\s*,\s*\d{1,3}\s*(,\s*(0|1|0?\.\d{1,6}|1\.0{1,6})\s*)?\)$`
  - token: `^[a-z][a-z0-9_-]{0,63}$`

  Tokens include the web's `text-color-14` (`web:src/components/editor/components/toolbar/selection-toolbar/actions/TextColor.tsx:173`) and `appflowy_them_color_tint1` (`web:src/utils/color.ts:1-7`). This grammar replaces Desktop's `_isReadableColor` (ES:212-219). That check only catches values whose parse throws, for example an rgba alpha of hundreds of digits that `tryToColor` turns into `Infinity.toInt()`. The web had no check at all. Renderers MUST still treat a color they cannot resolve as no color, and MUST NOT throw.

  *Confirmed by the user on 2026-10-02:* this one shared grammar (hex, `rgb()`/`rgba()`, theme token) applies on both clients, including dropping colour strings that either client keeps today but that match none of the three forms.
- **R23.** Known keys whose value fails its rule are dropped. They are not preserved as unknown attributes: a registered key's type is fixed by this version (section 4).
- **R24 (atoms).** `mention` and `formula` make their insert an atom. Atoms are covered in section 9.4.
- **R25 (one mark-to-style mapping on web).** The web MUST derive the elements, classes and styles for registered marks from one shared function, used by both the editor's `Leaf` (`web:src/components/editor/components/leaf/Leaf.tsx:52-132`) and the static renderer `StaticRun` (`web:src/components/database/components/cell/text/rich-text/RichTextCellContent.tsx:26-75`). Today the two are kept in step by hand, and a mark added only to `Leaf` disappears in grid, card and title display. Leaf-only keys (`font_family`, `reference`, `prism_token`, `class_name`, inline comments) stay in `Leaf`, outside the shared function.

## 7. Reserved keys

- **R26.** These keys MUST NOT be stored, and readers MUST drop them:
  - `atom_key`: the web editor's internal atom identity (`web:.../rich-text-slate.ts:28-34`). Today it is dropped only because it is not on the allowlist. With unknown keys preserved, it would leak into storage without this rule.
  - `find_bg_color`, `auto_complete`, `transparent`: appflowy_editor transient keys (`~/.pub-cache/git/appflowy-editor-01eccc6…/lib/src/editor/block_component/rich_text/appflowy_rich_text_keys.dart:8-13`).
  - `prism_token`, `class_name`: web decorations that `Leaf` renders.
  - any key that starts with `_`, including the internal packing key `_preserved` (section 8.4). The key pattern already excludes these.

  Future versions MUST NOT give these keys a stored meaning.

## 8. Unknown attributes: preservation

An **unknown attribute** is a key in an insert's `attributes` that is not in section 6 and is not reserved.

### 8.1 What is kept

- **R27.** A version 1 client MUST keep an unknown attribute when it reads it, carry it through edits, and write it back unchanged, if and only if all of these hold. Every rule is applied per insert:
  1. The key matches `^[a-z][a-z0-9_]{0,63}$` (lowercase snake case, at most 64 characters). It is not `__proto__`, `constructor` or `prototype`, and it is not reserved (R26). This excludes Desktop's document key `comment-ids`.
  2. The value is not `null` or `false` (R18).
  3. The value is a string, `true`, a finite number, an array or an object. An integer-valued number must lie within ±(2^53 − 1), because larger integers do not survive JavaScript (conformance `san-017`). This includes integer-valued floats as Dart's `jsonDecode` and `serde_json` read them (`1.0`, `9007199254740992.0`, `1e21`): Dart MUST test `v is double && v == v.truncateToDouble()` as well as `v is int` (conformance `san-030`).
  4. Nesting depth is at most 4. A primitive has depth 0, and an array or object has depth 1 + the largest depth among its members, where the largest depth over no members is 0. So `[]` and `{}` have depth 1 (conformance `san-027`). Members may be `null`, `false` or any of the above. No nested object may have a key `__proto__`, `constructor` or `prototype` (conformance `san-014`, `san-016`, `san-021`). Dart MUST NOT compute the maximum with `reduce`, which throws on an empty list.
  5. *Removed on 2026-10-02 by user decision.* Revision 2 capped each value at 8,192 bytes of RFC 8785 canonical JSON. There is no per-value size cap: a value of any size that meets rules 1-4 and 6 is kept, and the 200,000-byte delta cap (section 12) is the only size bound. No client needs a canonical JSON writer. The number is kept free so that rule 6 keeps its id; conformance ids `san-018` and `san-026` are retired, and `san-029` pins the absence of a cap.
  6. At most 32 unknown keys are kept per `attributes` object (and per mention, and per mention `data`): the first 32 valid keys **in UTF-16 code-unit order of the keys**, not in input order (conformance `san-019`, `san-025`). The cap does not apply to objects nested inside a kept value (conformance `san-031`). Input order is not stable across clients: Rust stores the delta through a `serde_json::Value` map, whose keys come back sorted (no `preserve_order` feature in `Cargo.lock`), while `JSON.parse` and `jsonDecode` keep insertion order.

  Every remaining rule is structural and deterministic: it depends only on the key, the JSON value and the keys' UTF-16 order, never on how a client serializes numbers or strings, so every client decides identically. A value that breaks any rule is dropped whole. Nothing is truncated or rewritten.

  *Confirmed by the user on 2026-10-02:* these rules (1-4 and 6) are final, and a value that breaks them is dropped rather than making the cell read-only; R28 makes that safe.
- **R28 (contract on future writers).** A future writer that needs an additive attribute outside these limits MUST set `min_v` (R17). This turns the limits into a promise: dropping a value that breaks them never loses data from a conforming writer.
- **R29.** Unknown mention fields and unknown members of a mention's `data` follow R27 rules 1-4 and 6, with two exceptions: the reserved keys of R26 do not apply inside a mention (section 9), and rule 2 drops only `null`, so `false` is kept (conformance `san-028`). This keeps the section 4 promise that new mention fields are additive, whatever values they use.

### 8.2 What is never done with them

- **R30.** Unknown attributes MUST NOT reach any renderer, CSS style, class name, URL opener, tooltip or editor style resolver. The web `Leaf` renders `font_family`, `reference`, `prism_token`, `class_name` and inline-comment keys straight from Slate text properties (`web:.../Leaf.tsx:50, 114, 130-134`). appflowy_editor renders `font_family`, `font_size` and `bg_color` from delta attributes. So unknown attributes MUST be kept out of both editors' text properties (8.4).
- **R31.** Unknown attributes MUST NOT be accepted from the clipboard. Paste is new content, not a preservation path: pasted fragments keep only registered keys. This applies to today's web paste flattening (`web:.../rich-text-slate.ts:144-190`) and Desktop paste (`dt:lib/plugins/database/widgets/cell/rich_text/rich_text_cell_paste.dart`). For mentions inside a pasted fragment:
  - a mention of a known type keeps only its registered fields (section 9.1). Its `label` is recomputed at save (R37);
  - a mention of an unknown type is pasted as its `label` as plain text, with the insert's other registered marks. Without a string label it is pasted as nothing.
- **R31b (copy and cut out of a cell).** What a cell puts on the clipboard MUST carry registered keys only, on both clients, and MUST NOT carry `_preserved` in any form.
  - Desktop: `_copySelection` normalizes with `keepUnknown: false` (`dt:.../rich_text/rich_text_cell_paste.dart:57-112`), and `keepUnknown: false` also drops an already packed `_preserved`. Otherwise `inAppJson` carries `_preserved` into documents, which paste in-app JSON as is (`dt:lib/plugins/document/presentation/editor_plugins/copy_and_paste/paste_from_in_app_json.dart:13-66`), and documents would then store it and, through `supportSliced`, spread it by typing. Unpacking on copy instead would put flat `font_family`/`font_size` in front of the document renderer and break R30.
  - Web: `withRichTextCellCopy.getFragment` already flattens through `pickMarks` (`web:.../rich-text-slate.ts:17-20, 144-190`). `pickMarks` MUST stay registered-only, and a test MUST pin that.

### 8.3 Formatting and merging

- **R32.** Any preserved attribute makes its insert formatted for the plainness check in 2.2 step 9 (conformance `env-040`).
- **R33.** Adjacent inserts merge only when their attributes, registered and preserved, are deep-equal: objects have the same key set (in any order) with deep-equal values, arrays have deep-equal members in the same order, and numbers compare by value (`1` equals `1.0`). The web compares `JSON.stringify` output today, which depends on key order (`web:.../rich-text-slate.ts:122-127`); it MUST compare sorted-key JSON instead. Dart MUST use structural equality (`DeepCollectionEquality` from `package:collection`; Dart's `1 == 1.0` is true). This is an equality test only, not a serialization, so it needs no canonical writer.

### 8.4 Editing: text typed inside a run keeps them

- **R34.** In both editors, a run's unknown attributes are packed into one internal text property, `_preserved` (an object). This property is never stored, renderers never read it, and on save it is unpacked into `attributes`.
  - **Web.** `richTextToSlateValue` packs the attributes (`web:.../rich-text-slate.ts:86-104`), and `slateValueToRichText` unpacks them (`:106-137`). Slate's `insertText` inserts into the current text node, so typed text inherits `_preserved` together with the registered marks.
  - **Desktop.** `normalizeRichTextCellDelta` / `_keptAttributes` pack the attributes (ES:96-208), and the save path unpacks them. Add `_preserved` to `AppFlowyRichTextKeys.supportSliced` in `configureEditorRichTextSliceAttributes` (`dt:lib/plugins/document/presentation/editor_globals.dart:38-43`). Without that, text typed at offset 0 of a run drops all attributes. At other offsets, `_customAppFlowyEditorSliceAttributes` already returns the previous run's attributes (`editor_globals.dart:84-95`). The list is process-wide; documents never contain `_preserved` because nothing writes it outside a cell (R31b).
  - **Two functions, not one.** Both clients MUST keep these apart, because the editor's own delta already carries `_preserved` and a single function that "drops `_preserved` from input" (R26, conformance `san-015`) would erase every preserved attribute on the first keystroke (Desktop's `updateDraft` normalizes the editor delta on every change, and `_contentFor`, `richTextCellContentKey` and copy share that normalization):
    - `sanitizeStoredDelta(delta)`: for stored, flat or pasted input. It applies sections 6-9 and drops any `_preserved` key it meets (R26). This is the conformance `sanitize` contract.
    - `normalizeEditorDelta(delta, {keepUnknown})`: for the editor's own packed delta. It sanitizes registered keys, and with `keepUnknown: true` re-checks the contents of `_preserved` against R27 and keeps them packed; with `keepUnknown: false` (paste, copy) it drops `_preserved`.
    - `pack(flat)` / `unpack(packed)` convert between the two shapes. Tests MUST assert `normalizeEditorDelta(normalizeEditorDelta(x)) == normalizeEditorDelta(x)`, `unpack(pack(x)) == sanitizeStoredDelta(x)` and `pack(unpack(y)) == y` for normalized `y`.
- **R35.** Typed text inherits `_preserved` exactly when it inherits the run's registered marks. Text typed next to an atom goes into a run of its own, with the atom's non-atom marks: web `textMarks` (`web:.../rich-text-slate.ts:51-58`), used by the `insertText` override (`:460-499`); Desktop's slice function drops only the `partialSliced` keys `mention` and `formula` (`editor_globals.dart:28-33, 97-114`). `_preserved` follows the same path. The atom keys and `atom_key` never carry over.
- **R36.** Removing registered marks from a run (for example un-bolding it) MUST keep its `_preserved`. Deleting the text deletes its attributes with it.

## 9. Mentions

### 9.1 Registry

A mention is the value of the `mention` attribute: an object with a non-empty string `type`. A mention stored as JSON text is decoded (WRT:89-100; RTD:207-223). A value that is not a mention by these rules is dropped, and its placeholder reads as text (conformance `san-006`, `pt-017`).

| Field | Type | Notes |
|---|---|---|
| `type` | non-empty string | Known types: `person`, `page`, `childPage`, `date`, `externalLink`. A legacy `reminder` is written back as `date` (conformance `san-009`); the web already does this (WRT:103), and Desktop MUST start doing it. |
| `page_id`, `block_id`, `row_id`, `date`, `end`, `reminder_id`, `reminder_option`, `url`, `person_id`, `database_id`, `database_view_id`, `database_row_id`, `row_document_id` | string | Kept only as strings (WRT:39-54). Desktop keeps them whatever their type today (ES:222-232) and MUST adopt this rule. |
| `person_name` | string | A finite number is written as its digits (WRT:124-127; RTD:234-236). |
| `include_time` | boolean | |
| `data` | object | `title` and `database_name` are kept only as strings. Other members follow R29. An empty `data` is omitted. A `data` that is not an object is dropped (conformance `san-010`). The web flattens `data` to primitives today (WRT:70-80); under R29 nested members within the limits are kept. |
| `label` | string | Section 9.2. A label that is not a string is dropped (conformance `san-024`). |
| any other | | Unknown fields, kept by R29 (conformance `san-008`). |

A **row mention** is a `page` mention with a non-empty `row_id` or `database_row_id`. Its `page_id` is the database view (WRT:324-326; RTD:194-196).

### 9.2 `label`

- **R37.** A version 1 writer MUST set `label` on every mention of a known type to exactly the text section 10 writes for it. The label is recomputed on every write (conformance `lb-001`, `lb-002`).
- **R37b (comparison keys ignore known labels).** The keys editors use to recognize their own save coming back, and to decide whether a draft is clean, MUST ignore `label` on mentions of known types (and keep it on unknown types, where it is content). On web that is `canonicalKey` (`web:src/components/database/components/cell/text/rich-text/RichTextCellEditor.tsx:101-103`, compared at `:216-239` against `pendingKeysRef`, which `write` fills at `:308` with the unlabelled draft's key). On Desktop it is `richTextCellContentKey` (ES:249, compared in `_onCellData`, ES:681). Without this, every save that adds a label looks like an outside change: a clean editor is replaced, its undo history cleared and the caret moved to the end; titles, which save on every keystroke, would jump after typing a mention.
- **R38.** A writer MUST NOT change the `label` of a mention whose type it does not know. If such a mention has no label, the writer MUST NOT add one (conformance `lb-003`).
- **R39.** Readers MUST ignore `label` for known types. They compute the text, because page names change (conformance `pt-013`, `pt-014`). For unknown types, readers MUST use `label` both as the plain text and as the displayed text, drawn as plain text in the surrounding style, without a link. If there is no string label, the mention reads as nothing and displays as nothing (today's corpus rule, conformance `pt-010`, `pt-015`). This replaces the empty chip on web (`web:src/components/editor/components/leaf/mention/MentionLeaf.tsx:47-75` renders nothing for an unknown type) and Desktop's "Not supported" label (`dt:lib/plugins/database/widgets/cell/rich_text/rich_text_cell_text.dart:397-402`).
- **R40.** A future mention type MUST carry a `label` that is the plain text its writer puts in `data`. Otherwise it is not additive (R17).

### 9.3 Person mentions in cells

Person mentions picked in a cell also carry `page_id` (the database view), `row_id`, and on the web `block_id` when present (`web:src/components/editor/components/panels/mention-panel/MentionPanel.tsx:954-966`; `dt:lib/features/mention_person/presentation/widgets/person/person_list.dart:186-196`). These are ordinary registered fields. Notification behavior is specified in `MENTION_NOTIFICATIONS.md`.

### 9.4 Placeholders and atoms

- **R41.** A mention or an equation sits on exactly one placeholder character, `$` or `@`. Desktop writes `$` (`dt:lib/plugins/document/presentation/editor_plugins/mention/mention_block.dart:87`) and the web writes `@` (`web:.../rich-text-slate.ts:23-26`). Readers MUST accept both. An atom attribute on any other character is dropped, the character becomes text, and the insert keeps its other attributes (ES:112-125; `web:.../rich-text-slate.ts:64-104`). Several placeholders in one insert are several atoms. This normalization runs when the editor opens and when it saves. It is not part of the conformance `sanitize` section, which maps each input insert to exactly one output insert.

## 10. Plain text (`data`)

- **R42.** `data` is the concatenation over inserts of:
  - **Mentions.**
    - `person`: `@` + the trimmed `person_name`, or `@` + `person_id` if the name is empty.
    - `date`: `@` + `MMM D, YYYY` in en-US format and local time, plus ` h:mm A` if `include_time` is true. A date string that cannot be parsed is written as is.
    - `externalLink`: its `url`.
    - `page` / `childPage`: the page's current name if the resolver knows it, else `data.title`. A row mention always uses `data.title`.
    - Any other type: its string `label`, else `""`.
  - **Formulas**: the LaTeX.
  - **Everything else**: the insert.

  This is today's rule (WRT:328-380; RTD:127-158, 225-277) plus the label rule. The conformance `plainText` section is normative. Cases `pt-001` to `pt-011` are the former 11-case corpus, copied verbatim.
- **R43.** The text is computed from the sanitized delta at save time. Page names are captured then, and not updated on rename (existing behavior).

## 11. Writer rules (version 1)

- **R44.** A version 1 writer MUST write `{"v": 1, "text": <data>, "delta": <delta>}`, where:
  - the delta is sanitized (sections 6-9);
  - every known mention is labelled (R37);
  - preserved attributes are written back (section 8);
  - `text` equals the `data` written in the same transaction (web) or the same changeset (Desktop: `data` and `rich_text` in one `Cell` map, DER:1459-1460).

  Key order does not matter. Rust's `json!` writes keys in sorted order.
- **R45.** If the delta formats nothing, the writer MUST NOT store an envelope. The web deletes the key (`web:.../dispatch/cell.ts:223-225`). Desktop writes `""`, and only if a non-empty string was there before (RT:139-147). Both stay as they are.
- **R46.** Version 1 writers never produce: `min_v`; non-string inserts; `retain` or `delete` ops; empty inserts; `null` or `false` attribute values; reserved keys; mentions as JSON text; unknown keys they did not read from the cell itself (R31); lone surrogates (R21); top-level fields other than `v`, `text` and `delta`.
- **R47.** A row duplicate, a field duplicate, and any other path that copies a cell, MUST copy `rich_text` verbatim. It MUST NOT re-serialize or sanitize it. In addition:
  - The copy MUST be Text-written exactly when the original is (section 0). For a Text-written original, copy `field_type` and `source_field_type` verbatim: no fallback to the field's current type, no normalization (conformance `ed-012`, `ed-026`). Today's web `cloneDatabaseCell` writes `getStoredCellFieldType(referenceCell, fieldType)` (`web:src/application/database-yjs/cell.clone.ts:24-26`), which turns a copy of a cell without `field_type` under a URL field into a URL-written cell.
  - Every shared Yjs value MUST be deep-copied (`value instanceof Y.AbstractType ? value.clone() : value`). Today's web clone copies only `Y.Array` (`cell.clone.ts:12-22`), so a future `Y.Map` key (R4) would throw mid-transaction: row duplicate catches per field and silently leaves the cell out (`web:.../dispatch/row.ts:897-914`), field duplicate (`web:.../dispatch.ts:2510-2523`) has no catch.
  - Desktop's `duplicate_row` copies the cell map (DER:89-130; integration test `rich_text_cell_test.rs:371-402`).

## 13. Write paths and guards

### 13.1 Guard rule

- **R49.** Every write to an existing **newer** cell (a Text-written cell in state `newer`, whatever the field's current type is) MUST be either a no-op or refused:
  - **No-op.** If the write would leave every non-bookkeeping key of the cell unchanged (section 0), it MUST write nothing at all: not `data`, not `rich_text`, not `field_type`, not `source_field_type`, not `last_modified`, not row attribution. It reports success (conformance `ed-005`, `ed-016`). This covers a same-text save from any editor, including a URL editor on a Text-written cell, whose write would otherwise stamp `field_type` 6 and make the cell non-Text-written for every reader (mobile `_handleMobileSubmitted` saves without a change check, `dt:lib/plugins/database/widgets/cell/editable_cell_skeleton/url.dart:389-394`; Rust URL cells are built with `new_cell_builder(FieldType::URL)`, pinned collab `url_type_option.rs:102-106`, and merged over the stored cell).
  - **Refused.** Any other write is refused and changes nothing: a change of `data` or `rich_text`, a change or removal of any other non-bookkeeping key, or the removal of the cell (conformance `ed-004`, `ed-006` to `ed-008`, `ed-010`, `ed-011`, `ed-017` to `ed-020`).
  - The no-op rule applies **only to newer cells**. Writes to other cells proceed as today, including same-`data` writes that change date options (`include_time`, `end_timestamp`, `is_range`, `reminder_id`; `web:.../dispatch/cell.ts:66-90, 233-238`) or normalize `field_type`.
- **R49b (bulk schema operations skip).** Operations that rewrite or delete many cells as a side effect of a schema change MUST leave newer cells untouched and proceed for every other cell (result `skipped`, conformance `ed-021` to `ed-024`). They do not show a notice: the user asked for a schema change, not for this cell. These are:
  - leaving a Created time or Last edited time field, which materializes the row timestamp into the cell (web `web:src/application/database-yjs/dispatch.ts:3943-3970`; Desktop `rs:flowy-database2-data/src/services/database/database_editor_field.rs:654-675`, which merges `{field_type, data}` with `cells.insert` and would overwrite the cell on Desktop too);
  - entering or leaving Created by or Last edited by, which deletes the cell (web only, `dispatch.ts:3934-3941`);
  - leaving a Formula field, which materializes the computed result (web `materializeFormulaResult`, `dispatch.ts:3499-3550`, deletes every key except `created_at`; Desktop `materialized_formula_cell` with `cells.insert` / `cells.clear`, `database_editor_field.rs:742-763`);
  - the web's legacy field-type normalizer, on a field switch (`dispatch.ts:3983-3988`) and on every row load (`installLegacyCellFieldTypeNormalizer`, `web:src/application/database-yjs/cell.field-type.ts:108-140`, installed at `web:src/application/services/js-services/cache/index.ts:530, 857`). It MUST skip a newer cell when moving `source_field_type` into `field_type` would make the cell non-Text-written (`ed-024`). It may proceed when the cell stays Text-written (`ed-025`).

  After such a switch a skipped cell still shows its own text (read-only) instead of a timestamp or computed value. That is visible but loses nothing, and it is what user decision 4 (revision 2.1) requires.

  *Confirmed by the user on 2026-10-02:* newer cells are protected during field-type switches. They are never overwritten or deleted by a switch; once the field is Text again they show read-only with their own text (while the field has another type, R52 governs what is displayed, e.g. Created by shows the row's creator).
- **R50.** A guard MUST read the cell state in the same transaction as the write, or under the same lock, so that no other write can come in between. On the web, the check runs inside the `runDatabaseRowAction` callback before the first `set`, and a refused or no-op callback returns without writing (Yjs records no undo item for an empty transaction).
- **R51.** Refusals MUST reach the user. The UI shows the update prompt (section 14). Desktop returns `ErrorCode::RichTextRequiresNewerClient` (section 18). No-ops and R49b skips are silent.
- **R52.** UI gating (making the cell read-only before an edit starts) is required for Text fields, but correctness MUST NOT depend on it. Under other field types (a Text-written newer cell after a switch to URL, Number, Select, ...) the guards and the save-error notice (R54) are the enforcement; read-only display there is optional.

- **R49c (undo and redo).** Before `DatabaseHistoryManager.replay` applies a stack group, it MUST find every cell the group's stack items would change and check each with `checkExistingCellWrite`. A Yjs `StackItem` holds `insertions` and `deletions` delete sets; iterate their structs (`Y.iterateDeletedStructs` inside a read-only `doc.transact`) and walk each item's `parent` chain up to the `cells.<fieldId>` map it belongs to. If any affected cell is newer and the replay would change a non-bookkeeping key of it, the group is not applied: it is removed from the stack with the existing `discardStackItem` (so the next undo continues with older history), and the update notice is shown. The guard is required because the claim "undo only reverts this client's own guarded writes" does not hold per cell: `Y.UndoManager` restores per **key** (`redoItem` blocks a value only if another client wrote that same key later), and a Desktop formatting-only save writes only `rich_text` (section 16). Undoing an older `data` change would then leave `data` and a newer envelope out of step, which is stale and lost for every version (compat F3).

### 13.4 Documented exceptions (user-chosen destruction)

These are deletions or restores of whole records, not cell edits. Guarding them would block a user action because of data the user cannot see.

- Deleting a row, field or database.
- Restoring a database or row history snapshot.

Converting a field out of Formula is no longer an exception: its materializer skips newer cells (R49b).

## 14. Update prompt (UX)

- **R53.** A `newer` cell is shown with its known formatting and is never opened in an editor. An attempt to edit it shows a notice with the key `grid.row.richTextRequiresNewerVersion`. Ways to edit include clicking the cell, pressing Enter or typing, pasting into a selected cell, focusing a title, or opening the calendar title.
  - Desktop (en-US): "This text was formatted in a newer version of AppFlowy. Update AppFlowy to edit it."
  - Web (en): "This text was formatted in a newer version of AppFlowy. Update AppFlowy (refresh this page) to edit it."

  A short form, `grid.row.richTextReadOnlyBadge` ("Read-only"), MAY label the cell. Both clients reuse their existing error toasts: web `notify.error`, Desktop `showToastNotification`.
- **R54.** A save refused by a guard shows the same notice, on every save path, whatever the field type:
  - Desktop: `ErrorCode.RichTextRequiresNewerClient` maps to the notice in `_showSaveFailedToast` (`rich_text_cell_editor.dart:183`) **and** in the generic `CellController.saveCellData` path (`dt:lib/plugins/database/application/cell/cell_controller.dart:296-345`). Today that path drops errors when the caller passes no `onFinish` (URL saves at `editable_cell_skeleton/url.dart:171, 394` do), so a refused URL or Number save would fail silently. The read-only gate cannot cover those cells, because only rich-text controllers have a `richTextStore` (`cell_controller_builder.dart:88-106`).
  - Web: every guarded helper returns its refusal to the dispatch hook, which calls `notify.error(t('grid.row.richTextRequiresNewerVersion'))` once per user action (a multi-row drag or a clear-field shows one notice).

## 15. Compatibility with released clients

Released desktop and web clients have no rich text at all.

- They read and write only `data`. They never write or remove `rich_text`. Released web sets `data` alone. Released Rust builds a `{field_type, data}` cell and merges it in, so the key is kept (RT:135-147 explains the merge).
- When a released client changes the text, every version reads the formatting as `stale` (R3). The formatting is lost to readers. That is accepted, and it is the reason for R3.
- **A→B→A resurrection.** If a released client changes the text from A to B, and later back to exactly A, the old envelope describes `data` again and reappears. This includes a `newer` envelope, which makes the cell read-only again. Versioned clients avoid this for their own writes: a plain write that changes the text clears the envelope (web deletes it, Rust writes `""`; TTO:155-165; `web:.../dispatch/cell.ts:226-231`). Released clients cannot be fixed. The risk is narrow, because the text has to come back exactly.
- Released clients copy the key on row duplicate. They keep formatting through field type round trips that do not rewrite cells.
- Released clients ignore `v` and `min_v`, so they cannot protect `newer` cells. Versioning protects cells only among versioned clients.

## 16. Concurrency

- `rich_text` is one opaque string under Yjs last-writer-wins per map key. There is no character-level merge of concurrent formatting edits (RT gotcha 4).
- A writer sets `data` and `rich_text` in one transaction. On web that is the `runDatabaseRowAction` callback, which `set`s both keys. On Desktop it is one cell `insert`: DER:1587-1589 merges the new cell's keys with `Any::fill` (pinned collab `rows/cell.rs:24-33`).
- **Correction (revision 2).** `Any::fill` writes a scalar with `try_update` (pinned collab `core/fill.rs:51-53`), which creates a Yjs item only when the value changed (yrs `map.rs:238-258`). So a Desktop save that changes only the formatting creates a new `rich_text` item and **no** new `data` item. Revision 1 claimed both keys are always written together; that is true on web only. Consequences:
  - Concurrent writers can resolve `data` and `rich_text` to items from different writers. Whenever that leaves `text ≠ data`, the envelope is stale and every reader falls back to plain text (R3). No reader shows mismatched formatting.
  - Web database undo restores per key and can revert `data` alone under a newer client's later formatting-only save. R49c guards it.
  - A frozen invariant "every formatting write also writes `data`" was considered and rejected: version 1 Rust cannot satisfy it without changing collab, and it would bind future clients to a write pattern rather than to an observable rule.
- When a released client concurrently sets only `data` and wins, the envelope is stale, and every reader falls back to plain text.
- A concurrent write by a newer client and a version 1 client is resolved by last-writer-wins, like any two concurrent edits. The guard sees only the state at write time (R50). Losing one of two concurrent edits is not specific to versions.
- The Desktop key merge means Rust never removes keys it does not set. That is why clearing writes `""` (RT:135-147), and why unknown cell keys (R4) survive Desktop writes.

## 17. Upgrade path

- Lazy, with no migration. Envelopes without `v` (written by today's pre-release builds) read as version 1 (R9; conformance `env-004`). The next version 1 save writes `"v": 1`.
- **R55.** A version N reader MUST accept every envelope from versions 1 to N, and MUST apply R3 and R10 to all of them.
- A future version that adds a non-additive feature sets `min_v` only on cells that use it. All other cells stay editable by version 1.
